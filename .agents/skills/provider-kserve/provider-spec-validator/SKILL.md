# Provider Spec Validator

Audit provider-kserve's parameter surface by scanning each topology's Go type definitions and
reconcile-time validation, then comparing the result against three declared-schema sources: the
UI form schema (`topology.yaml`), the human-readable parameter table (`README.md`), and the
generated OpenEverest provider spec (`charts/provider-kserve/generated/provider-spec.yaml`).

Use this skill when the user asks for any of the following:
- "missing parameters"
- "check topology.yaml against types.go"
- "validate the README parameter table"
- "audit UI field wiring"
- "is this validation rule mirrored in the UI"
- "fix schema drift"
- "is the generated spec stale"

Default behavior is **audit only**. Do not edit files unless the user explicitly asks for fixes
or approves a proposed fix plan.

---

## Usage

```bash
/provider-spec-validator                 # Full audit: all topologies
/provider-spec-validator llm              # Audit only definition/topologies/llm
/provider-spec-validator predictor        # Audit only definition/topologies/predictor
/provider-spec-validator readme           # Focus on README.md parameter table drift only
/provider-spec-validator --fix            # Audit, present plan, then fix after approval
```

If scope is unclear, ask:

```text
Should I audit all topologies, just llm, just predictor, or only the README parameter table?
```

## Source of truth

### Code sources (what a parameter actually does)

| Area | Source | Notes |
|---|---|---|
| Topology parameter struct | `definition/topologies/<topology>/types.go` | The `<Topology>TopologyParameters` struct — the ground truth of which fields exist |
| Custom JSON decoding | same file, `UnmarshalJSON` method, when one exists | See "The UnmarshalJSON trap" below — this is the highest-value check in this skill |
| Shared component types | `definition/components/types.go` | `VllmCustomSpec` and friends — parameters that live on a component, not the topology |
| Reconcile-time validation | `internal/provider/*.go`, every `func validate*` | e.g. `validateLLM`, `validateRoutingGroup`, `validateLoRAParams`, `validateLoRASlots`, `validatePredictor` in `llminferenceservice.go` / `inferenceservice.go` |
| Object-building (what a parameter actually changes on the cluster) | `internal/provider/llminferenceservice.go` (`buildLLMInferenceService`), `internal/provider/aigateway.go`, `internal/provider/inferenceservice.go` | Confirms a documented parameter has a real effect, not just a validated-and-ignored field |
| Topology dispatch | `internal/provider/provider.go` | `Validate`/`Sync` switch on `c.Instance().GetTopologyType()` |

### Declared schema sources (what a user is told exists)

| Area | Source |
|---|---|
| UI form schema: field groups, labels, helper text, CEL validation, field ordering | `definition/topologies/<topology>/topology.yaml` |
| Human-readable parameter reference table | `README.md` (the `\| Parameter \| Type \| Description \|` tables) |
| Generated OpenEverest provider spec | `charts/provider-kserve/generated/provider-spec.yaml` — **generated by `provider-sdk generate` from `definition/`. Never hand-edit. Regenerate with `make generate`.** |
| Design rationale for a non-obvious parameter or validation choice | `docs/adr/*.md` |
| Domain glossary (what a term means, what to call it instead) | `CONTEXT.md` |

`provider-spec.yaml` is a build artifact, not something to diff field-by-field by eye — its own
file header says so (`# This file is generated by 'provider-sdk generate' from definition/
files. Do not edit manually. Run 'make generate' to update.`). Checking it for drift means
running `make generate` and looking at `git diff`, exactly what `make verify` already does in
CI (`Makefile:103-111`). Do not hand-parse it looking for missing fields — that check is
mechanical, not comparative.

## Workflow overview

1. **Preflight** — confirm scope, check git status, avoid edits unless approved.
2. **Extract actual parameter inventory** — scan each topology's Go struct fields.
3. **Check `UnmarshalJSON` coverage** — the sharpest, most repo-specific check this skill does.
4. **Derive actual validation behavior** — trace every `validate*` function.
5. **Extract declared schema inventory** — `topology.yaml` fields/paths/CEL, README table rows.
6. **Compare inventories** — missing, stale, unwired, path-mismatched, validation-mismatched.
7. **Report findings** — actionable tables with file/line references.
8. **Fix with approval, then validate** — `make generate && make verify`, `go test`, chainsaw.

## Step 2: Extract actual parameter inventory from Go types

For each topology, list every struct field with its JSON tag, Go type, and doc comment:

```bash
for f in definition/topologies/*/types.go; do
  echo "--- $f"
  awk '/TopologyParameters struct/,/^}/' "$f"
done
```

Record, per field:
- Field name and Go type (note `*int32`/`*bool`/`*string` vs bare — pointer fields are
  "optional, nil means unset", not "optional, zero value means unset")
- JSON tag (this is the wire name every other source must match exactly)
- Doc comment (this is usually the only place the *why* and the *requires/conflicts-with*
  relationships are written down)
- Whether a helper method reads it (`grep -n "t\.<FieldName>" definition/topologies/<t>/types.go`
  — an unread field is a dead parameter)

---

## Step 3: Check `UnmarshalJSON` coverage — read this section carefully

This is the single highest-value check in this skill, and it is specific to how this repo's
topology types work. Several `<Topology>TopologyParameters` types define a custom
`UnmarshalJSON` (see `definition/topologies/llm/types.go:129`) because Everest's form generator
sends flag fields as `"true"`/`"false"` strings, not JSON booleans, and the type needs to accept
both.

**The trap:** a hand-written `UnmarshalJSON` decodes into a raw `map[string]json.RawMessage` and
then handles each field explicitly, one `if v, ok := raw["fieldName"]; ok { ... }` block at a
time. There is no fallback generic decode. If a field is added to the struct in step 2 but no
corresponding block is added here, that field is **silently always its zero value** — no error,
no panic, no CI failure that catches it. A user can set the field in the UI or in raw YAML, and
it will be quietly dropped before validation or Sync ever sees it.

Check this for every topology that defines a custom `UnmarshalJSON`:

```bash
for f in definition/topologies/*/types.go; do
  if grep -q "func (t \*.*TopologyParameters) UnmarshalJSON" "$f"; then
    echo "=== $f has a custom UnmarshalJSON — checking field coverage ==="
    echo "-- struct fields (json tags):"
    awk '/TopologyParameters struct/,/^}/' "$f" | grep -oE '`json:"[a-zA-Z]+' | sed 's/`json:"//'
    echo "-- fields explicitly handled in UnmarshalJSON:"
    awk '/func .*UnmarshalJSON/,/^}/' "$f" | grep -oE 'raw\["[a-zA-Z]+"\]' | sed -E 's/raw\["|"\]//g' | sort -u
  fi
done
```

Any struct field's JSON tag that does not appear in the "explicitly handled" list is a real bug:
report it as **field silently dropped on unmarshal**, not as a documentation issue. This is a
correctness bug, not a drift-in-docs issue, and belongs at the top of the report regardless of
what else is found.

## Step 4: Derive actual validation behavior

Read every `validate*` function reachable from `Provider.Validate` (`internal/provider/provider.go`):

```bash
grep -n "^func validate" internal/provider/*.go
```

For each one, record as a rule:
- What field(s) it reads
- The condition that triggers an error, and the exact error message
- Whether it is a **pairing rule** (field A requires field B, or A and B are mutually exclusive
  — e.g. `validateRoutingGroup` in `internal/provider/llminferenceservice.go:143` requires
  `RoutingGroup` and `TrafficWeight` together, and requires `EnableGatewayRouting`)
- Whether it is a **range/pattern rule** (min/max, regex)
- Whether it depends on another field's *value*, not just presence (e.g. rejected when
  `ExternalAccess == EnvoyAIGateway`)

This is the inventory you compare against the UI's CEL expressions in Step 6.

## Step 5: Extract declared schema inventory

### 5a. `topology.yaml` UI fields

```bash
for f in definition/topologies/*/topology.yaml; do
  [ -f "$f" ] || continue
  echo "=== $f"
  echo "-- fields with a wired path:"
  grep -n "path: spec.topology.parameters\." "$f"
  echo "-- CEL validation expressions:"
  grep -n "celExpr:" "$f"
  echo "-- componentsOrder blocks:"
  grep -n "componentsOrder:" "$f"
done
```

Note `.topology.yaml.disabled` files (e.g. `definition/topologies/predictor/topology.yaml.disabled`)
separately — a disabled topology's Go types are not held to UI-wiring rules, but are still held
to the `UnmarshalJSON` coverage and README checks if the topology is otherwise documented as
available.

For every field with a `path:` entry, check it also appears in its section's `componentsOrder`
list. A field defined but missing from `componentsOrder` is wired but never rendered — same
practical effect as not existing, harder to notice because the YAML looks complete.

### 5b. README parameter tables

```bash
grep -n "^| \`" README.md
```

Record each row's parameter name, type, and description text.

### 5c. Generated provider spec (mechanical check only)

```bash
make generate
git diff --quiet -- charts/provider-kserve/generated/ config/ && echo "generated files up to date" || git diff --stat -- charts/provider-kserve/generated/ config/
```

If this reports drift, that is the entire finding for this source — do not also hand-diff
`provider-spec.yaml`'s contents against `types.go`. Revert any incidental generated-file changes
this produced before continuing the audit, unless the user asked for `--fix` and approved
committing regenerated output.

## Step 6: Compare inventories

### 6a. Field coverage mismatches

| Type | Meaning |
|---|---|
| Silently dropped on unmarshal | Struct field has no matching `raw[...]` block in a custom `UnmarshalJSON` (Step 3) — always report first, this is a correctness bug |
| Missing in `topology.yaml` | Go field exists, no `path:` entry anywhere in the topology's UI schema — confirm with the field's doc comment whether this is deliberate (internal-only / legacy alias) before flagging as a gap |
| Wired but unordered | Field has a `path:` entry but its key is missing from that section's `componentsOrder` — never renders |
| Missing in README | Go field with a UI `path:` entry has no corresponding row in the `README.md` parameter table |
| Stale in `topology.yaml` or README | A `path:` or table row references a field no longer in the Go struct |
| JSON path mismatch | `path: spec.topology.parameters.<x>` does not match any struct field's `json:"<x>"` tag exactly (case-sensitive) — the UI writes to a key the Go struct never reads |

### 6b. Validation mismatches

For every pairing/range rule found in Step 4, check whether `topology.yaml` has a matching
`celExpr`. Flag:

- **Go validates, UI does not warn** — a Go `validate*` rule (e.g. "`trafficWeight` requires
  `routingGroup`") has no corresponding `celExpr`, so a user can submit an invalid combination
  in the UI and only find out when the reconcile loop rejects it.
- **UI's error message references a field the UI never wired.** This is the class of bug found
  live in this repo: `definition/topologies/llm/topology.yaml:228` has a `celExpr` that reads
  `spec.topology.parameters.enableGatewayRouting`, with a message telling the user to set
  "Enable Gateway Routing" — but no `path:` entry for `enableGatewayRouting` exists anywhere in
  the file, so there is no UI control by that name for the user to find. Always cross-reference
  every field name mentioned inside a `celExpr` or its `message` against Step 5a's field list.
- **UI restricts more than Go does** — a `celExpr` rejects something the Go validator actually
  allows. Lower priority than the two above, but still worth reporting: it blocks a valid
  configuration for no server-side reason.

### 6c. Effect mismatches

For a parameter that passes both Go and UI validation, confirm it actually does something:
`grep -n "topo\.<FieldName>\|params\.<FieldName>" internal/provider/*.go` outside the
`validate*` functions. A field read only inside its own validator and nowhere in a `build*`
function is validated-and-ignored — report it as **no observed effect**, and note this needs a
human check (the read may be legitimately indirect, e.g. via a method like
`UsesAIGateway()`/`MetricsEnabled()` rather than the field itself).

## Step 8: Fix mode

Only enter fix mode after the user asks for `--fix` or approves the proposed plan.

### 8a. Fix priority

1. **`UnmarshalJSON` coverage gaps** first — these are silent correctness bugs, not doc drift.
2. **`topology.yaml` wiring fixes** (missing `path:`, missing `componentsOrder` entry, a
   `celExpr` referencing an unwired field) when the Go side is correct and the UI is behind.
3. **README table fixes** when the code and UI are both correct and the table is stale.
4. **Go struct/validation changes** only after explicit confirmation — changing what a parameter
   means or how it validates can be a breaking change to any `Instance` already using it.

### 8b. Edit rules

- Never hand-edit `charts/provider-kserve/generated/provider-spec.yaml` or anything under
  `config/`. Run `make generate` and commit its output instead.
- Keep a topology's `UnmarshalJSON` field handling in the same order as the struct definition —
  this repo's existing files do, and it is what makes the coverage check in Step 3 easy to
  re-run by eye later.
- When adding a `path:` entry to `topology.yaml`, also add the field's key to the relevant
  section's `componentsOrder` list in the same edit — Step 6a exists because this is exactly the
  step that gets forgotten.
- When a `celExpr` needs a field it doesn't have, check whether the field already has a `path:`
  elsewhere in the file before assuming one needs to be added.
- Match README table wording style to the existing rows in the same table — short sentence,
  states what the field does and its precondition, no marketing language.

### 8c. Validate after edits

```bash
make generate
make verify
go test ./...
```

If a fix touched `internal/provider/*.go` validation logic, also run the package directly:

```bash
go test ./internal/provider/... ./definition/topologies/...
```

Report all validation results, including the `make verify` diff if it is not clean.

## Mandatory rules

- **Always scan Go types first.** They are ground truth for what a parameter is and does; UI
  schema and README are declarations *about* that ground truth, and can drift independently.
- **Always check `UnmarshalJSON` coverage before anything else** when a topology defines one —
  it is a silent-correctness-bug class specific to this repo's custom decoding, not a
  documentation nicety.
- **Never treat `provider-spec.yaml` as something to hand-diff.** Run `make generate` and read
  `git diff`; that is the entire check.
- **Always cross-reference field names inside a `celExpr` and its `message`** against the
  file's own `path:` entries — a validation message can reference a UI control that was never
  wired, and the CEL expression will still evaluate fine, so nothing else catches this.
- **Include file:line references** for every finding.
- **Do not flag a field missing from `topology.yaml` without checking its doc comment first** —
  some fields are deliberately UI-invisible (legacy aliases, internal-only), and the doc comment
  is usually where that intent is recorded.
- **Do not edit `internal/provider/*.go` validation behavior without explicit approval** —
  changing what passes or fails validation can break an existing `Instance`.
- **After fixes, run `make generate && make verify` and report the result.** A fix that leaves
  generated output stale is not finished.
- **When a finding is really an architecture question** (which component should own a rule, or
  whether a validation gap traces back to an upstream behavior) rather than a same-repo drift
  fix, hand it to `/ks-grill` instead of resolving it here.
