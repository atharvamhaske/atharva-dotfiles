# DevOps / Platform Engineering Reference

Working notes on the platform layer backend systems actually run on top of: Kubernetes, GitOps, and the observability/CI tooling around them. Useful for Day B (design) and Day C (debugging) problems that are really "your service is fine, the platform under it isn't."

## Kubernetes: the reconciliation model

The single fact almost everything else derives from: Kubernetes is a **desired-state reconciliation system**, not an imperative task runner. You declare what you want (a Deployment with 5 replicas of image `v2`); controllers continuously compare desired state to observed cluster state and take actions to close the gap. Nothing "runs a deploy" in the imperative sense — a controller notices actual replica count doesn't match desired and creates/deletes Pods until it does, on an ongoing loop, forever. This is why Kubernetes recovers automatically from a node dying (the controller notices missing Pods and recreates them elsewhere) but also why a bad rollout doesn't "fail loudly" the way a script would — it just keeps reconciling toward a broken desired state until something (a readiness probe, a human, an automated rollback policy) intervenes.

**Pods, Deployments, Services — the layering:** a Pod is the smallest deployable unit (one or more tightly-coupled containers sharing network/storage); a Deployment manages a ReplicaSet of Pods and owns rollout behavior (rolling update, rollback, revision history); a Service is a stable virtual IP/DNS name load-balancing traffic across whichever Pods currently match its label selector — Pods are inherently ephemeral (IPs change on every restart), Services are what give callers something stable to talk to.

**Readiness vs. liveness probes:** liveness failing gets the container killed and restarted (for "it's stuck, nuke it" recovery); readiness failing just pulls the Pod out of Service load-balancing without killing it (for "it's alive but not ready for traffic yet," e.g. still warming a cache). Conflating the two is a classic production bug: a slow-starting service with only a liveness probe set too aggressively gets killed in a restart loop before it ever finishes starting, because nothing distinguished "not ready yet" from "dead."

**Rolling updates and PodDisruptionBudgets:** a rolling update replaces old Pods with new ones incrementally (`maxSurge`/`maxUnavailable` control the pace) so capacity never drops to zero — but this only prevents *self-inflicted* disruption during deploys. A PodDisruptionBudget separately protects against *voluntary* cluster-initiated disruption (node draining for maintenance, cluster autoscaler scaling down) by capping how many Pods of a given app can be down at once for any reason, not just deploys.

**Horizontal Pod Autoscaler (HPA):** scales replica count based on observed metrics (CPU/memory by default, custom metrics — e.g. queue depth, request rate — via metrics adapters) against a target. The interview-relevant subtlety: HPA reacts to *current* load with a real lag (metric collection interval + new-Pod startup time), so a traffic spike faster than that reaction window still causes a latency blip even with a correctly configured HPA — this is what predictive/scheduled scaling and generous readiness buffers exist to soften.

## GitOps (Argo CD-shaped systems)

GitOps applies the same reconciliation idea to deployment itself: a Git repository is the single source of truth for desired cluster state, and an in-cluster controller (Argo CD) continuously compares live cluster state to what's declared in Git, applying diffs to converge — rather than a CI pipeline pushing changes *into* the cluster imperatively (`kubectl apply` from a pipeline runner with cluster credentials).

**Why this matters operationally, not just philosophically:** the cluster never needs to expose credentials to an external CI system (the controller pulls, nothing pushes in with cluster-admin), every change is a Git commit (full audit trail, trivial rollback via `git revert`), and drift — someone running `kubectl edit` directly against the cluster — gets detected and can be automatically reverted back to match Git, which is the property that actually prevents "it works because someone hand-patched it in prod and nobody remembers" from silently happening.

**Sync vs. drift, and the failure mode worth knowing:** a stuck/failing sync (a manifest that's invalid, a resource stuck terminating, a webhook rejecting the apply) leaves the cluster in a state that matches neither the old nor the new Git state — diagnosing this means checking the controller's sync status/health per-resource, not just "is the Git commit merged," since merged-to-main and actually-applied-to-cluster are two different facts that GitOps intentionally decouples (and that decoupling is exactly where "I merged it, why isn't it live" incidents come from).

**App-of-apps / multi-cluster patterns:** managing many clusters/environments from one GitOps setup typically uses a parent "app of apps" pattern (one Argo Application that itself manages a set of other Applications) so that promoting a change through dev → staging → prod is a Git operation (merging a branch, updating a values file) rather than a manual per-cluster action — this is the piece that makes GitOps scale past a single cluster.

## Prometheus and Grafana

**Prometheus** is a pull-based metrics system: it scrapes HTTP endpoints (`/metrics`) on a configured interval rather than services pushing metrics to it — this shapes a lot of downstream design, e.g. short-lived batch jobs need a Pushgateway intermediary since Prometheus can't scrape something that's already finished. Its data model is a metric name plus a set of key-value labels (e.g. `http_requests_total{method="GET", status="200"}`), and its query language (PromQL) does aggregation/rate math over that labeled time-series data — `rate(http_requests_total[5m])` for a per-second rate over a trailing window is the single most common query shape in practice.

**The counter/gauge/histogram distinction matters for correctness:** a counter only increases (resets to 0 on restart, which `rate()` is specifically designed to handle correctly by ignoring the reset), a gauge can go up or down (current value, e.g. in-flight requests), and a histogram buckets observed values (e.g. request duration) to support percentile estimation via `histogram_quantile()` — using a gauge where a counter belongs (or vice versa) silently produces meaningless rate/percentile math downstream, which is a real, easy-to-make configuration bug.

**Grafana** is the visualization/alerting layer on top of Prometheus (and other data sources) — dashboards are queries against the underlying metrics store, not a separate data store themselves, so a "Grafana is showing wrong numbers" incident is almost always actually a PromQL query bug or an underlying Prometheus/scrape issue, not a Grafana bug per se.

**Alerting design:** alerting directly on a raw threshold (e.g. "CPU > 90%") is noisy and often wrong; alerting on **symptom** (SLO burn rate, elevated error rate, latency percentile breach) rather than **cause** (CPU, memory) is the standard practice, because symptom-based alerts page you for things users actually feel, while cause-based alerts page you for things that may or may not matter (CPU at 95% with headroom-to-spare autoscaling configured is not an incident).

## CI/CD platforms (Harness-shaped systems)

Modern CI/CD platforms (Harness and similar) generally provide, on top of raw pipeline execution: **progressive delivery** (canary or blue-green rollouts with automated analysis — shift a small percentage of traffic to the new version, evaluate real metrics against the old version, auto-promote or auto-rollback based on that comparison, rather than a human eyeballing a dashboard), **policy-as-code gates** (a deploy can be blocked by an automated policy check — e.g. required approvals, security scan results — before it's allowed to proceed), and **feature-flag integration** (decoupling *deploy* from *release*: new code ships dark behind a flag, and turning user-facing behavior on is a separate, instantly-reversible action from the deploy itself).

**The design principle worth internalizing for interviews:** deploy and release are different operations. A bad deploy caught by canary analysis auto-rolls-back at the infrastructure level; a bad *feature* (correctly deployed, but the logic itself is wrong) gets turned off via a flag flip, instantly, without any redeploy at all — conflating these two mechanisms (treating every bad outcome as "redeploy the previous version") is slower and riskier than it needs to be for the subset of failures that are actually flag-shaped.

## Practical interview framing

A representative Day C problem here: "a Deployment rollout to `v2` is stuck at 3/5 new Pods ready, the other 2 are in `CrashLoopBackOff`, and Argo CD shows the Application as `OutOfSync`." Working it correctly means separating *application-level* investigation (why is v2 actually crashing — check `kubectl logs`/`describe` on the failing Pods) from *platform-level* investigation (is this a resource-limit issue, a readiness-probe misconfiguration, a PodDisruptionBudget blocking the rest of the rollout, or a GitOps sync that's only partially applied) — a good candidate identifies which layer the incident lives in before proposing a fix, rather than guessing at the application code first.
